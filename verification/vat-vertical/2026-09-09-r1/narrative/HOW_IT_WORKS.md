# How the modern VAT rule works — plain English

Pack `atu-merlin-ts-vat-v1@1` · Conversion commits `02a9916` … `b6d3af0` on PR [#1](https://github.com/ashosborne/atuMerlin/pull/1) · Verification run `2026-09-09-r1`

## What moved

One small Discovery slice — the IBM i service program `FVAT` (module `VAT300`), the single place in the estate that turns a one-character VAT code into a rate and a VAT amount — was rebuilt as a shared TypeScript module, `modern/src/shared/fvat`. Nothing else moved. The `VATDEF` table already existed in the modern Postgres schema as a read-only dependency of the ORD vertical; the VAT pack takes over its meaning and documents it without altering a column. There is no screen and no HTTP endpoint for VAT, on purpose: the legacy never exposed VAT except through the programs that called it, and the modern order code already calls the shared module for every order line.

## How the new path works

- **Four small functions, the same four the legacy exported.** `getVatRate` and `getVatDesc` return the rate and the description stored for a code; `clcVat` returns the VAT *amount* (not the gross — the caller adds it to the net) for a code and a net amount; `existVatRate` says whether a code is present and not soft-deleted. The arithmetic is the legacy's: net × rate ÷ 100, rounded half away from zero to two decimals, computed in whole hundredths so no binary floating-point rounding can creep in. Verification checked it against a literal re-evaluation of the RPG statements on more than two million value pairs, including every awkward tie at the third decimal and the extremes of the legacy field sizes; they agree everywhere.
- **The legacy's quirks are kept, deliberately.** An unknown code gives a rate of zero and a VAT amount of zero with no error — the "VAT silent zero" planted defect — because that is what the box does and whether it *should* raise is an open SME question. A code flagged as deleted is still applied by the three getters and only refused by `existVatRate`, exactly the inconsistency in the source. A blank code never touches the table at all (Verification counted the SQL statements: zero), so a row keyed with a blank would be invisible, as on the box. A longer code is cut to its first character, as the one-character by-value parameter did for free in RPG.
- **One thing is different, and documented as such.** The legacy remembered the last code it looked up for the life of the job, so a rate changed mid-session was not seen until the program asked for a different code and came back. The modern server is stateless and reads the table on every call — Verification counted seven reads for seven calls — so a changed rate is applied at once. That is recorded as CR-V1, not hidden; whether rates ever change intra-day on the box is the SME question that decides whether anyone would notice.
- **No maintenance, no seed of its own.** The legacy had no program to create, change or list VAT rates; rows arrived by restore or direct SQL. The modern side is the same: the only thing that writes `vatdef` is the ORD development fixture (three rates: 5.5 %, 20 %, 10 %). Whether the target should treat VAT rates as seed configuration or gain a maintenance screen is a room decision the pack leaves open (CR-V4).

## What Verification checked, and what it did not

Verification ran the type checker and the 201 TS-boundary tests (27 of them for VAT) against a live Postgres, then ran an independent probe whose expected values were written from the Discovery cards through a different arithmetic (exact BigInt decimals, two-step truncate-then-round as the RPG source reads) — not copied from the module or its tests. The probe swept every cent between −1 000.00 and 1 000.00 at nine rates, 200 000 random net/rate pairs across the full legacy field ranges, and 4 500 calls through the table; wrapped the database pool to count statements for the "never reads" and "no cache" claims; drove the unknown-code path with 94 codes; checked the delete-flag truth table, the export surface, the code normalisation and the table's column types and bounds. All 23 cases passed. It then walked the ten cards (nine matched or matched-with-explained-residual, one recorded absence), confirmed every planted defect is still there, dispositioned the four deliberate deltas (three acceptable for the demo, one deferred to the room) and recorded one contract observation (G-V1: the module normalises the one-character code but not the two-decimal net; no modern caller can reach the difference).

It did **not** compare against the IBM i. There are no legacy goldens for this pathfinder, so the result is `TS_BOUNDARY_GREEN` under the `WAIVED_PATHFINDER` waiver, never `PARITY=GREEN`. The honest one-liner is: **VAT residual verified at TS API under waiver — not Merlin migrated.**
