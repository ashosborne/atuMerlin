# How the modern application log works — plain English

Pack `atu-merlin-ts-log-v1@1` · Conversion commits `2b0fa73` … `666330d` on PR [#1](https://github.com/ashosborne/atuMerlin/pull/1) · Verification run `2026-09-09-r1`

## What moved

The smallest Discovery slice in the estate, and the one with the least to move. On the IBM i, the "application log" is a 5 000-byte user space called `SAMLOG`: a one-off program (`LOG100`) creates it by hand beside the `PARAMETER` file and writes a seven-byte header; a one-procedure service program (`LOG300.AddLogEntry`) appends lines of the form `User: <who> * Date: <when> * Msg: <what> ***` at a write cursor kept in the space's first four bytes; exactly one thing in the whole estate ever calls it — the order-line delete trigger `ORD700` — and the only way to read it is a menu option that runs a display command whose source is not in the tree. The ORD vertical, converted and verified earlier under its own pack, already writes that one event to a Postgres table named `samlog`. So the LOG pack did not build a second log. It added one shared TypeScript module, `modern/src/shared/samlog`, whose single procedure writes to the **same** table with the **same** actor rule as the ORD trigger, so a line written by either is indistinguishable; plus a formatter that rebuilds the legacy line string from a row, a decoder that reads the legacy byte layout from a copied user space, and four comments on the existing table. No table, route, page or reader was added. Nothing in the ORD code was touched.

## How the new path works

- **One procedure, one insert.** `createSamlog(db).addLogEntry(entry, user?)` is the service program's one export. It cuts the message at 500 characters and then trims blanks from both ends — in that order, because the legacy parameter was a fixed 500-byte field and `%trim` ran on the field, not on the caller's string — and inserts a row with the message, the actor and the database's local timestamp. It returns nothing, as the legacy procedure returned nothing. A blank or empty message still writes a row; the legacy did no validation and neither does this. Verification compared 500 module writes and 3 000 trimmed entries against a `500A + %trim` oracle written from the card, exactly.
- **The actor is per event, and it is the ORD trigger's rule.** If the caller names a user, that name (cut to ten characters, case kept) is stored. If not, the row's actor is `ord700_user()` — the Postgres function the ORD pack wrote for its trigger: the `atu.user` setting of the current transaction if the ORD repository set one, else the database role. Verification showed the module's row and the trigger's row in one transaction naming the same user. The legacy stamped `User` once when the service program was first activated in a job and kept it for the job's life; the modern module records it per event, which is what the ORD pack already chose and had verified. That difference is recorded as CR-L4 and the SME brief still asks whether per-event is the intended contract — nobody here answered it.
- **The legacy line string is reproducible, not stored.** `formatLegacyLine(row)` rebuilds `User: ` + the user padded to ten + ` * Date: ` + a 26-character `YYYY-MM-DD-HH.MM.SS.UUUUUU` timestamp + ` * Msg: ` + the message + ` ***`, and then applies the legacy's 500-byte line buffer — so a message longer than 437 characters is cut and loses its ` ***` terminator, exactly as on the box, where a separator-based reader would then glue it to the next line. Verification compared 3 000 rebuilt lines with a replay of the RPG concatenation, character for character, including the card's own example line. The stored message is *not* cut at 437 (CR-L3): the cut is a property of the line buffer, not of the message, the only in-tree caller writes ≈ 64-character messages, and the string is recoverable from the row either way. Whether that string is a contract for anything is a question for the room; nothing in the tree reads it.
- **The byte layout survives as a decoder over a copy.** `decodeSamlogUserSpace(buffer)` reads the big-endian cursor at offset 0, checks the `***` marker at offset 4, takes the bytes from 7 to the cursor and splits them on ` ***` — the rule the c09 card spells out for a reader that does not exist in the tree. Verification built 200 user spaces with a JavaScript replay of `LOG100` + `LOG300` (header, 600-byte padded writes, cursor advanced by the logical length) and decoded them back to the lines written; it also built one in EBCDIC and showed the default decoding fails on it while the injectable text and terminator recover it, so the "an EBCDIC copy needs the box's CCSID" note is exercised rather than assumed. No migration of existing `SAMLOG` content was performed or recommended.
- **Three legacy defects are recorded, not reproduced — and Verification watched them not happen.** The user space had a hard capacity: with `ORD700`-sized lines the replay fills 5 000 bytes after **35** writes and then every later write fails silently and permanently, because the failing write happens before the cursor moves; the modern table has no capacity and kept all 60 (CR-L5). The legacy resolved the user space once per job and, if that failed, never tried again while swallowing every later error; the modern module throws a plain database error to the caller when the table is missing and simply works on the next call once it is back (CR-L6). The legacy's write cursor was shared by every job with no lock, so two simultaneous writers overwrote each other; the replay under the card's own interleaving loses one line per racing pair and leaves blank runs, while 200 concurrent modern appends were all kept (CR-L8).
- **Nothing was invented.** There is no `LOG100` equivalent, no reset or truncate, no reader route or page, no OpenAPI entry, no second `shared/logging` module, and the ORD trigger still writes its own row — the LOG module is imported by nothing under `modern/src`. All of that was checked for absence.

## What Verification checked, and what it did not

Verification ran the type checker and the 306 TS-boundary tests (24 of them for LOG) against a live Postgres, then ran an independent probe whose expected values were written from the Discovery cards and the cited RPG source, not copied from the module or its tests: it replayed `LOG100` and `LOG300` as a byte machine and compared the line string on 3 000 triples, the trimmed message on 3 000 entries, the timestamp form on 1 500 values round-tripped through the table, and the decoder on 200 machine-built spaces plus an EBCDIC copy; it deleted 300 order lines and compared the ORD trigger's row, the LOG module's row and the message oracle three ways; it checked the export surface, the table's shape and comments, the schema section's additivity, and the absence of any reader or reset; and it replayed the capacity, initialisation and concurrency defects to show the modern deltas are the deltas the README declares. All 18 cases passed on three runs. It then walked the ten cards (four matched at the boundary, six residual with a reason that traces to the pack, three of those with the delta observed), confirmed every planted behaviour is still there, dispositioned the eight deliberate deltas (all eight acceptable for the demo; the decisions the code waits on — preserve the log at all, is the line string a contract, is per-event actor intended — are the room's and the SME's) and recorded two observations: the module's parameter type does not admit the transaction client the documented actor alignment relies on (it works at runtime, one type widening away), and the width constants count characters where the box counted single-byte EBCDIC bytes (identical for everything an in-tree caller can produce).

It did **not** compare against the IBM i. There are no legacy goldens for this pathfinder, so the result is `TS_BOUNDARY_GREEN` under the `WAIVED_PATHFINDER` waiver, never `PARITY=GREEN`. It did not claim the slice has business value — the pack itself says the whole thing may be a non-functional side effect, and the module has no caller. The honest one-liner is: **LOG residual verified at TS API under waiver — not Merlin migrated; the `SAMLOG` user space and its reader stay on IBM i, and the room still decides whether the user-space log is preserved at all.**
