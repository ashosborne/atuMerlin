# How the modern country lookup works — plain English

Pack `atu-merlin-ts-cou-v1@1` · Conversion commits `e90dfb2` … `418d5cf` on PR [#1](https://github.com/ashosborne/atuMerlin/pull/1) · Verification run `2026-09-09-r1`

## What moved

Half of one Discovery slice. The IBM i service program `FCOUNTRY` — two small modules, `COU300` (look a country code up: name, ISO-3 code, does it exist) and `COU301` (the "Select a Country Code" pop-up window the customer and supplier screens open on F4) — was rebuilt as a shared TypeScript module, `modern/src/shared/fcountry`. The other half of the slice, the `COU200` "Work with Countries" maintenance panel that creates and changes country rows, did **not** move: the pack defers it, nothing of it was written, and Verification checked that nothing in modern writes to the `country` table except the development seed. The `country` table itself already existed in the modern Postgres schema as a read-only dependency of the customer vertical; the COU pack takes over its meaning, adds the by-name index the legacy logical file provided, and documents it without altering a column.

## How the new path works

- **Three getters, one read each.** `getCountryName`, `getCountryIso3` and `existCountry` each do a single keyed read of `country` by the two-character code. An unknown code gives a blank name, a blank ISO-3 and `false` with no error — that is what the box does. A blank code never reads the table at all (Verification counted the SQL statements: zero), so a row keyed with a blank would be invisible, as on the box. A longer value is cut to two characters, as the two-character by-value parameter did for free in RPG; case is not folded, because the uppercasing was the 5250 session's doing, not the program's.
- **The selector as data, not as a screen.** `sltCountry` is the window's list: position at a code (or, in the by-name order, at a name), return the next twenty rows and say whether there are more — exactly the legacy's twenty-row load with its one-row look-ahead that decides between "More..." and "Bottom". The rules the window enforced on Enter — a row option must be 0 or 1, only one row may carry 1, the control line accepts only 0 or 8, position-to is refused while a selection is pending, F8 flips between by-code and by-name and is ignored while options are typed — are a small pure function (`sltCountryCheck` / `sltCountryAct`) that returns the same indicator numbers and message texts the DDS carried (35, 36, 41, 42), so a future web selector can show them without re-deriving anything. There is no web page and no HTTP endpoint for the selector yet: the customer form keeps its simple datalist, and the pack leaves the decision to the room.
- **The legacy's quirks are kept, deliberately.** `getCountryIso3` exists and nothing calls it, because nothing on the box called it either and whether to carry or drop it is an open SME question. A position beyond the last country gives an empty list with no message, as the window did. Pressing F8 to switch orders clears the position of the order you are entering, so after toggling away and back the list starts from the top and the caller's own country code is no longer the starting point — Verification reproduced the card's exact four-step trace. Whether the target should behave better on either point is a room decision, not this pack's.
- **One thing is different, and documented as such.** The legacy remembered the last code it looked up for the life of the job and skipped the read on a repeat; the modern server is stateless and reads on every call — Verification counted five reads for five calls where the box would do one. A country renamed mid-session is therefore seen at once instead of at the next code switch. That is recorded as CR-C1, not hidden; `country` has no writer in modern, so it cannot happen in the demo anyway. Sorting is by byte order rather than the mainframe's EBCDIC order; for the upper-case codes and capitalised names in use the two agree, and where they would not (codes starting with a digit, names starting lower-case) is recorded as CR-C4 — with a correction to the README's wording, which claimed more agreement than there is.

## What Verification checked, and what it did not

Verification ran the type checker and the 306 TS-boundary tests (41 of them for COU) against a live Postgres, then ran an independent probe whose expected values were written from the Discovery cards, not copied from the module or its tests: it fetched every country row with a plain query, replayed the legacy's keyed read in JavaScript (position, twenty rows, look-ahead) and compared 1 020 pages in both orders over 53 rows including digit and lower-case codes, duplicate names and accented names; it modelled the window's Enter-key rules as a separate state machine and compared the module against it on a 512-row truth table, 192 F8 combinations and 1 500 random sessions; it wrapped the database pool to count statements for the "never reads" and "no cache" claims; it drove 668 unknown codes; it checked the table's column types and bounds, the by-name index, the export surface, and that nothing in modern maintains countries. All 27 cases passed. It then walked the six cards (all six matched at the boundary, with the cache and the binder metadata explained as residual), confirmed every planted behaviour is still there, dispositioned the five deliberate deltas (four acceptable for the demo, one — the missing window presentation — deferred to the room) and recorded four observations, none of which changes an answer for any input reachable in modern today.

It did **not** compare against the IBM i. There are no legacy goldens for this pathfinder, so the result is `TS_BOUNDARY_GREEN` under the `WAIVED_PATHFINDER` waiver, never `PARITY=GREEN`. The honest one-liner is: **COU FCOUNTRY residual verified at TS API under waiver — not Merlin migrated; the COU200 panel half is still on IBM i.**
