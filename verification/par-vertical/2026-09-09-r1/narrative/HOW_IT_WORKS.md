# How the modern parameter store works — plain English

Pack `atu-merlin-ts-par-v1@1` · Conversion commits `19609fc` … `cb8142d` on PR [#1](https://github.com/ashosborne/atuMerlin/pull/1) · Verification run `2026-09-09-r1`

## What moved

One small Discovery slice with one live purpose. On the IBM i, the `PARAMETER` file is a two-key key/value table maintained by the `PAR200` "Work with Parameters" screen and read through the `FPARAMETER` service program (`GetPARM1` … `GetPARM5`). The whole subsystem serves a single row: `PATH`, the IFS directory every generated file in the estate is written under — read by the order PDF print, two purchasing exports and the `PAR201` "Work with IFS output" utility. It was rebuilt as a shared TypeScript module, `modern/src/shared/parm` (the five getters plus a named `getPath()` for the one call everybody makes), a small JSON API under `/api/parameters` standing in for the `PAR200` screen (list, open, create, update, delete, and a `GET /api/parameters/path` reader), and one Postgres table, `parameter`, appended to the modern schema. Nothing else in modern changed: the customer and order verticals were not touched, the order feature still makes no `PATH` read (its PDF step is an open question under its own pack), and no `PATH` row is seeded — its presence and value are installation data, as on the box.

## How the new path works

- **Five getters, one read each.** `getParm1` … `getParm5` each do a single keyed read of `parameter` by the two ten-character keys and return one typed column. An unknown key gives blanks and zeros with no error — that is what the box does. A blank code *and* blank sub-code never reads the table at all (Verification counted the SQL statements: zero), so the blank-keyed row the screen can create is invisible to the getters, as on the box. A longer key is cut to ten characters and trailing blanks are ignored, as the ten-character by-value parameter did for free in RPG; case is not folded — `path` and `PATH` are two different rows — because the uppercasing was the 5250 session's doing, not the program's.
- **`getPath()` is the configuration seam.** It is nothing more than `GetParm2('PATH', ' ')` given a name, so a converted consumer reuses the configuration value instead of reading the table itself. The value comes back exactly as stored: no trailing slash is added or removed (two of the four legacy consumers need one, and whether the value on the box has it is a data question nobody has answered), and a missing or blank `PATH` is an empty string with no error, as on the box. The `PAR201` utility's pattern string (`<PATH>*`, which lists a directory only if the path ends with `/`) is reproduced as a pure function; the interactive IFS browser it opened is not.
- **The screen as an API, with the screen's rules.** `POST` creates a row after the one check `PAR200` made — is the key already there? — and nothing else: a blank key is fine, values are not validated, there is no audit and no success message. Keys and the two short value fields are folded to upper case on the way in, because the 5250 device did that for every field without `CHECK(LC)` and it is the only reason a `PATH` row typed in lower case is ever found; the long `PARM2` keeps its case as the screen's `CHECK(LC)` allowed. `PUT` updates the five values unconditionally, key fixed, even if nothing changed; `DELETE` removes the row at once with no confirmation and no "is anything using this?" check — `PATH` included — and answers the same whether or not the row existed. The list comes back in key order, fourteen rows at a time with an exact "more / bottom" from a one-row look-ahead, and shows the first 32 characters of `PARM2`, as the subfile did.
- **Three things are different, and documented as such.** The legacy remembered the last key it looked up for the life of the job and skipped the read on a repeat; the modern server is stateless and reads on every call — Verification counted five reads for five calls where the box would do one, and a `PATH` edited or deleted through the API is seen by the next call rather than by the next job. That is recorded as CR-P1, not hidden. The screen's subfile quirks — a list that did not refresh after a create, a duplicate row after "Bottom", a blank ghost row after a delete, record locks held while a panel was open — do not exist over HTTP, where every list request is a fresh read (CR-P2). And where the legacy raised an unmonitored exception into the session (updating a row that had vanished, losing a create race), the API answers 404 or the same duplicate error (CR-P5). Sorting is by byte order rather than the mainframe's EBCDIC order; for the upper-case keys the API writes the two agree, and where they would not is recorded as CR-P3 — with a correction to the README's wording, which claimed more agreement than there is.
- **The big question is deliberately left open.** Discovery recommended treating `PATH` as target configuration — an environment setting — rather than a maintained row, which would retire the screen and the table altogether. Conversion did not decide that: it mapped the file to a table so that every card holds as written, and put `getPath()` in front so that a switch to configuration later is a second implementation behind the same interface, not a change to any consumer. Verification checked that nothing was invented on either side: no configuration reader, no web page, no OpenAPI file, no seeded row.

## What Verification checked, and what it did not

Verification ran the type checker and the 306 TS-boundary tests (40 of them for PAR) against a live Postgres, then ran an independent probe whose expected values were written from the Discovery cards, not copied from the module or its tests: it replayed the legacy service program's read-with-cache in JavaScript and compared it with the module on 1 810 getter calls over 62 rows and 300 unknown keys, on 2 000 key spellings for the ten-character contract, and on SQL statement counts to show the deliberate no-cache delta as a delta; it fetched every row with a plain query, replayed the screen's fourteen-row keyed read and compared the list page by page on ten table sizes; it modelled the create, edit and delete panels from the cards and compared them with the API on 400 random creates, 200 random edits, a 24-way concurrent create race and every delete case the cards name; it compared the `PAR201` pattern on 3 000 values; it checked the table's columns, bounds, constraints and comments, the export surface, the six-route HTTP surface and the absence of anything more. All 22 cases passed on three runs. It then walked the thirteen cards (ten matched at the boundary, three residual with a reason that traces to the pack), confirmed every planted behaviour is still there, dispositioned the seven deliberate deltas (all seven acceptable for the demo; the decisions the code waits on — `PATH` as configuration, the trailing-slash data fact, a web page, the estate's list/edit lock template — are the room's and the SME's) and recorded four observations, none of which changes an answer for any input the modern writer can produce.

It did **not** compare against the IBM i. There are no legacy goldens for this pathfinder, so the result is `TS_BOUNDARY_GREEN` under the `WAIVED_PATHFINDER` waiver, never `PARITY=GREEN`. The honest one-liner is: **PAR residual verified at TS API under waiver — not Merlin migrated; PAR201's IFS panel and the PATH-as-configuration decision are still on IBM i / open.**
