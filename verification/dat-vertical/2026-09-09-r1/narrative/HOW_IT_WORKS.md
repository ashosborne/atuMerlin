# How the modern DAT utilities work — plain English

Pack `atu-merlin-ts-dat-v1@1` · Conversion commits `03e8bc1` … `5957461` on PR [#1](https://github.com/ashosborne/atuMerlin/pull/1) · Verification run `2026-09-09-r1`

## What moved

One small Discovery slice — the two IBM i SQL scalar functions `ISOTODATE40` (program `DAT002`) and `ISO_Num_To_Date` (program `DAT001`) that turn the estate's eight-digit numeric dates (`yyyymmdd` in an `8 0` column) into real dates — was rebuilt as a shared TypeScript module, `modern/src/shared/dat`, plus two small SQL functions appended to the Postgres schema. Nothing else moved. The IBM i functions themselves, the query-management reports that might call them, and the copies of the same date rule inside CUS200 and ORD202 stay where they are. Nothing in the modern CUS or ORD code calls the new module yet: each of those packs still carries its own copy of the rule, and adopting the shared one is a decision for their next version, not this pack's.

## How the new path works

- **Two as-is functions for comparison.** `isoToDate40` reproduces `ISOTODATE40` exactly as the source reads: `0` becomes `1940-01-01`, `99999999` becomes `2039-12-31`, a well-formed `yyyymmdd` (any year 0001–9999, real months and days, 29 February only in leap years) becomes that date, and anything else becomes "no value". `isoNumToDate` reproduces `ISO_Num_To_Date`: the same, minus the two special values. They are pure — same answer every time, nothing remembered between calls — and a missing argument gives a missing result without running, exactly as the IBM i declared (`RETURNS NULL ON NULL INPUT`, `DETERMINISTIC`, `NO SQL`).
- **The date lock the rest of modern shares with ORD.** Inside the modern boundary a "never" date is simply `NULL`. The IBM i shapes — the number `0`, or the `1940-01-01` value the screens used to blank out — appear only when a value crosses that boundary, through four small helpers (`fromLegacyIsoNum`, `toLegacyIsoNum`, `fromLegacySentinelDate`, `toLegacySentinelDate`) and two SQL twins (`dat_iso_num_to_date`, `dat_date_to_iso_num`). The outbound SQL twin computes exactly what the ORD701 trigger already computes inline when it stamps a customer's last-order date, so the two packs agree by construction. `2039-12-31` is deliberately **not** treated as "never": the legacy never blanked it either, and whether any real data holds `99999999` is an open SME question.
- **The error path.** The IBM i programs failed the whole SQL statement with SQLSTATE `38I02` if the packed argument was corrupt. In TypeScript the only equivalent is a value an `8 0` field could not hold (not an integer, or beyond ±99999999), and the module raises `DatArgumentError` with the same SQLSTATE and the same 70-character message limit. An invalid *date* is not an error — it is "no value", as on the box.
- **No HTTP, no table.** The pack's contract is empty on purpose: the legacy exposed this rule only through SQL callers, so a shared module and two SQL functions are the whole surface.

## What Verification checked, and what it did not

Verification ran the type checker and the 201 TS-boundary tests (63 of them for DAT) against a live Postgres, then ran an independent probe whose expected values were written from the Discovery cards through a different calendar routine — not copied from the module or its tests. The probe swept every month/day combination 00–99 for thirteen chosen years (130 000 numbers) plus 200 000 random values across the whole `8 0` range, negatives included; pushed the same sweep through the two SQL functions; checked the declared function attributes; and read the ORD schema and trigger text to confirm the lock has the same shape ORD uses. All 29 cases passed. It then walked the eight cards (seven matched, one residual with a stated reason), confirmed the known-risk behaviours are still there, dispositioned the four deliberate deltas (three acceptable for the demo, one deferred to the CUS pack), and found one documentation over-claim (G-D1: the README's "one sentinel rule" identity holds for zero and valid dates only, because the lock folds invalid dates into "never" and DAT002 does not).

It did **not** compare against the IBM i. There are no legacy goldens for this pathfinder, so the result is `TS_BOUNDARY_GREEN` under the `WAIVED_PATHFINDER` waiver, never `PARITY=GREEN`. The honest one-liner is: **DAT residual verified at TS API under waiver — not Merlin migrated.**
